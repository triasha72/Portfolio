A technical answer is only as useful as the evidence it can point back to.

AeroRAG-X is a production-oriented retrieval-augmented generation system over a curated NASA Technical Reports Server corpus. I built it to make retrieval, answerability, citation validity, deployment, and operational behavior independently measurable rather than hidden behind a single “chatbot quality” impression.

At a glance

  • 3,233 citation-preserving chunks
  • BM25 + dense retrieval + Reciprocal Rank Fusion
  • Cross-encoder reranking
  • Evidence-sufficiency gating and grounded refusal
  • OpenAI Responses API + deterministic local provider
  • Claim-level citation resolution
  • FastAPI + Docker + Cloud Run
  • Prometheus + OpenTelemetry + load validation
  • Held-out generation evaluation tracked separately

The engineering question

RAG systems fail in several different places: the source corpus can be wrong, chunk provenance can disappear, retrieval can miss the evidence, generation can answer when evidence is insufficient, citations can point to the wrong source, and an API can be “up” while the actual model runtime is broken. AeroRAG-X treats those as separate engineering problems with separate tests and telemetry.

Retrieval before generation

The corpus is built from NASA NTRS metadata and PDFs with versioned manifests, checksums, page-level extraction, and citation-preserving overlapping chunks. Retrieval is evaluated independently using BM25, Sentence Transformer dense retrieval, Reciprocal Rank Fusion, and a cross-encoder reranker.

The point of keeping these numbers separate is diagnostic: an LLM should not be allowed to hide a retrieval regression by producing a plausible answer anyway.

Generation is gated by evidence

Before a provider is called, the pipeline checks whether the retrieved evidence is sufficient for the requested claim. Numeric support, named anchors, qualifiers, and supported synthesis patterns are checked deterministically. Unsupported questions are refused rather than routed blindly to the LLM.

The final 32-query development benchmark recorded 100% answerability accuracy, 100% unsupported refusal, 100% claim-citation coverage, and 100% structural validity under the selected configuration. Those numbers are development-benchmark results, not a claim of universal RAG correctness.

The held-out result stays held out

A separate 12-query deterministic set was kept outside the 32-query development benchmark and was not used to choose retrieval or sufficiency settings. It recorded 0.9167 answerability accuracy and 0.8333 unsupported refusal, with full claim-citation and citation-reference validity. I keep that result visible because a held-out set stops being evidence if it becomes another tuning target.

Serving and observability

The same RAG runtime is used by the CLI and FastAPI service. Runtime loading happens once at application startup. The service exposes health, readiness, structured errors, request IDs, and a query endpoint. Docker runs non-root with read-only runtime artifacts.

Operational behavior is instrumented with structured JSON logs, Prometheus metrics, OpenTelemetry traces, detailed stage timings, provider telemetry, and deterministic HTTP load validation. The service is deployed privately on Google Cloud Run Gen2 with read-only Cloud Storage artifact mounts.

What this project demonstrates

For me, the important part is not the acronym RAG. It is the systems boundary: data provenance, retrieval, ranking, model-provider behavior, evaluation, API contracts, containers, cloud deployment, traces, metrics, and regression policies are all part of the model once the model is expected to serve users.
